# Android 版本选择评估

日期：2026-11-10。状态：调研与建议，尚未实现多版本功能，也未调整默认镜像。

建议保留当前环境，增加经过验证的旧版本作为兼容性对照。默认版本依据目标宿主机上的启动、安装和应用运行结果选择，不能由个别 APK 的失败直接推断“统一降级就能修复”。

## 官方镜像与宿主限制

本次读取 Google 官方 [Android TV](https://dl.google.com/android/repository/sys-img/android-tv/sys-img2-3.xml) 与 [Google TV](https://dl.google.com/android/repository/sys-img/google-tv/sys-img2-3.xml) 目录，二者均提供稳定 channel-0 的 ARM64 API31、33、34、36（Android12、13、14、16）。详细条目、revision、压缩大小、摘要、目录获取时间见[证据摘要](../testing/evidence/runtime-version-options-2026-11-10.json)。

第一阶段建议在 Apple Silicon 上评估 Android TV12 / API31 与现有 TV16 / API36 两档。API31 ARM64压缩镜像为763,104,604字节；已有官方大小和摘要，HEAD返回200且长度一致。尚未完整下载、解包或启动该镜像，不能把目录/下载地址有效当作 APK Checker 已支持。

相同旧API的Intel目录条目为x86，不能直接当作现有x86_64配置使用；Emulator兼容、宿主加速与ARM转译均需分别验证。各宿主只展示实际可用且经过验证的选项。

## 对已知问题的影响

- 儿歌多多只有 `armeabi-v7a` 原生库。Android版本降低不会自动产生ARM32支持；必须在启动镜像后读取真实 `ro.product.cpu.abilist` / `abilist32` / `abilist64`，再用原包实测安装。ARM64镜像名称不能证明或排除32位兼容。
- 宝宝趣学的Linux TV16对照已经捕获业务代码的空对象异常。旧系统可用于排查是否与平台行为有关，但不能承诺修复；若数据读取始终产生空对象，仍需应用方处理。详见[原包诊断](../testing/education-apk-compatibility.md)。
- 对存储、权限、后台执行或平台API变化造成的问题，多个真实系统版本能提供更有意义的对照。

## 产品与实现建议

1. 安装时选择设备类型与系统版本；按需下载，不把所有镜像塞入安装包。显示实际Android版本、支持架构、下载量及已准备状态。
2. 每个版本使用独立AVD与应用安装记录。保留当前设备及数据；切换系统不清空旧设备，不在原有数据目录上直接降级。当前 `installed[phone|tv]`、设置与IPC均只标识一种模式，需要一起扩展到明确的环境ID。
3. 导入时解析APK的最低系统与原生库信息；安装前根据真实设备ABI检查明确的不兼容情况，并解释“系统版本不满足”或“架构不匹配”。不能只根据宿主CPU推断兼容。
4. 增加崩溃诊断导出，分别记录安装、入口解析、前台确认和应用异常；桌面说明不作为启动失败证据。

下一步应先完成API31原始镜像的下载校验、私有AVD启动与真实ABI检查，再对原APK执行同条件测试，之后决定支持矩阵和默认环境。此次仅调研，未改变用户数据、启动新CI或发布安装包。
